Behat no Projeto

Uma explicação didática do que é Behat, por que ele existe no Moodle e como ele foi usado para validar o plugin de Informações de Tutoria.

Resumo rápido

Behat é uma ferramenta de teste automatizado que simula uma pessoa usando o Moodle pelo navegador.

Enquanto um teste PHPUnit verifica regras internas do código, o Behat verifica fluxos de uso reais:

  • entrar como estudante;
  • abrir a página da disciplina;
  • ver se os contatos aparecem;
  • entrar como professor;
  • adicionar a atividade pelo seletor de atividades;
  • confirmar que a interface aparece como esperado.
Ideia principal: Behat responde à pergunta: “um usuário real consegue fazer isso no Moodle?”

Behat em palavras simples

O Behat lê arquivos escritos em uma linguagem quase natural, chamada Gherkin. Esses arquivos têm frases como:

Given I am on the "Course 1" course page logged in as "student1"
Then I should see "Your support point"
And I should see "Polo Bataguassu"

Essas frases não são só documentação. O Moodle tem vários “passos” prontos que transformam essas frases em ações reais no navegador.

Então, quando o teste roda, ele realmente abre o Moodle, cria dados de teste, faz login, navega e confere textos na tela.

Diferença entre PHPUnit e Behat

Ferramenta Verifica Exemplo neste projeto
PHPUnit Regras internas do PHP, funções, serviços e dados. “Se o shortname contém REO, Mediador Pedagógico não é esperado no modo automático.”
Behat Fluxos reais de usuário no Moodle pelo navegador. “O estudante abre a disciplina e vê o Tutor Presencial e o Mediador Pedagógico do próprio Polo.”
Analogia: PHPUnit testa o motor por dentro. Behat dirige o carro pela rua para ver se ele funciona para quem usa.

Por que usamos Behat neste plugin?

Este plugin tem uma decisão importante de UX: a informação deve aparecer direto na página da disciplina, sem clique, como conteúdo inline.

Isso é algo que vale testar pelo navegador, porque envolve o Moodle inteiro:

  • curso/disciplina;
  • usuários;
  • papéis;
  • grupos/polos;
  • atividade Moodle;
  • renderização inline na página do curso;
  • activity chooser;
  • visão do estudante e visão do professor.

PHPUnit consegue testar as regras internas, mas Behat garante que o fluxo integrado do Moodle continua funcionando.

Arquivo criado no projeto

O teste Behat do plugin está em:

tests/behat/inline_display.feature

Esse arquivo descreve três cenários principais:

  1. Estudante vê os contatos do próprio Polo inline na página da disciplina.
  2. Professor vê a lista completa inline na página da disciplina.
  3. Professor consegue adicionar a atividade pelo seletor de atividades do Moodle.

Como o teste prepara os dados

Antes dos cenários, o Behat cria um mundo de teste temporário. Ele cria:

  • uma disciplina chamada Course 1;
  • um estudante;
  • um professor;
  • um Tutor Presencial;
  • um Mediador Pedagógico;
  • os papéis institucionais mod_tutor e mod_medpdg;
  • um grupo chamado Polo Bataguassu;
  • os membros desse grupo;
  • uma instância da atividade uemsinfotutoria.

Isso significa que o teste não depende de dados manuais existentes no Moodle. Ele monta tudo que precisa, roda, e depois o ambiente de teste é limpo pelo Moodle.

Exemplo do cenário do estudante

Scenario: Student sees their polo contacts inline in the course page
  When I am on the "Course 1" course page logged in as "student1"
  Then I should see "Your support point"
  And I should see "Polo Bataguassu"
  And I should see "Ana Tutora"
  And I should see "Maria Mediadora"
  And I should see "My polo"
  And I should see "Full list"

Esse cenário confirma o fluxo central do plugin:

  • o estudante entra direto na disciplina;
  • não precisa clicar na atividade;
  • o plugin aparece inline;
  • o Polo é identificado;
  • Tutor Presencial e Mediador Pedagógico aparecem.

Exemplo do cenário do professor

Scenario: Teacher sees the full course team inline in the course page
  When I am on the "Course 1" course page logged in as "teacher1"
  Then I should see "Tutoring and pedagogical mediation team"
  And I should see "Ana Tutora"
  And I should see "Maria Mediadora"
  And I should not see "My polo"

Esse cenário confirma que o professor não recebe a experiência de estudante “Meu polo”. Ele vê a equipe completa da disciplina.

Exemplo do cenário com JavaScript

O terceiro cenário usa a tag @javascript, porque ele abre o seletor de atividades do Moodle, que depende de comportamento dinâmico no navegador.

@javascript
Scenario: Teacher can add the activity from the activity chooser
  Given I log in as "teacher1"
  And I am on "Course 1" course homepage with editing mode on
  And I click on "Add an activity or resource" "button" in the "New section" "section"
  And I click on "Add a new Tutoring information" "link" in the "Add an activity or resource" "dialogue"
  And I set the following fields to these values:
    | Name | Tutoring contacts |
    | Student panel title | Support contacts |
  When I press "Save and return to course"
  Then I should see "Tutoring and pedagogical mediation team" in the "New section" "section"

Esse teste garante que o plugin aparece no seletor de atividades e pode ser adicionado por um professor.

Como configuramos o Behat neste ambiente

O Moodle precisa de um ambiente separado para testes Behat. No config.php local, adicionamos:

$CFG->behat_prefix = 'bht_';
$CFG->behat_dataroot = '/var/www/behatdata';
$CFG->behat_wwwroot = 'http://moodle45-app';
$CFG->behat_profiles = array(
    'chrome' => array(
        'browser' => 'chrome',
        'wd_host' => 'http://127.0.0.1:4444/wd/hub',
        'capabilities' => array('browserName' => 'chrome'),
    ),
);

O prefixo bht_ faz o Behat usar tabelas separadas no banco. Assim ele não mistura dados de teste com o Moodle normal.

O behat_dataroot também é separado, para arquivos temporários do ambiente de teste.

Por que usamos Selenium?

Para cenários com @javascript, o Behat precisa controlar um navegador real. Para isso usamos o Selenium.

No nosso ambiente Docker, subimos um container com Chromium:

docker run -d \
  --name moodle45-selenium \
  --network container:moodle45-app \
  --shm-size=2g \
  selenium/standalone-chromium:latest

O detalhe importante é:

--network container:moodle45-app

Isso faz o Selenium compartilhar a rede do container do Moodle. Assim, de dentro do Moodle, o endereço 127.0.0.1:4444 aponta para o Selenium.

Comandos usados

Inicializar o ambiente Behat

docker exec moodle45-app php /var/www/html/admin/tool/behat/cli/init.php

Rodar os testes Behat do plugin

docker exec moodle45-app bash -lc \
  'cd /var/www/html && vendor/bin/behat \
   --config /var/www/behatdata/behatrun/behat/behat.yml \
   --profile=chrome \
   mod/uemsinfotutoria/tests/behat/inline_display.feature'

Rodar só cenários sem JavaScript

docker exec moodle45-app bash -lc \
  'cd /var/www/html && vendor/bin/behat \
   --config /var/www/behatdata/behatrun/behat/behat.yml \
   mod/uemsinfotutoria/tests/behat/inline_display.feature \
   --tags="~@javascript"'

Resultado obtido

Depois da configuração, o Behat rodou com sucesso:

3 scenarios (3 passed)
40 steps (40 passed)

Isso significa que os três fluxos descritos no arquivo inline_display.feature passaram.

Conclusão: o plugin foi validado não apenas por regras internas em PHPUnit, mas também por fluxos reais no navegador com Behat.

O que esse teste protege no futuro?

Se alguém alterar o plugin e quebrar algum comportamento importante, o Behat pode avisar.

Exemplos de regressões que esse teste ajudaria a detectar:

  • o plugin parar de aparecer inline na página da disciplina;
  • o estudante não ver mais o Polo;
  • o Tutor Presencial sumir por erro de renderização;
  • o Mediador Pedagógico sumir por erro de papel/grupo;
  • o professor passar a ver a aba “Meu polo” indevidamente;
  • a atividade sumir do seletor de atividades;
  • o formulário da atividade quebrar.

Limitações

Behat é poderoso, mas não deve testar tudo.

  • Ele é mais lento que PHPUnit.
  • Testes com navegador podem depender de Selenium.
  • É melhor usar Behat para fluxos críticos de usuário, não para cada detalhe interno.

Por isso, neste projeto usamos uma combinação:

PHPUnit

Para regras de domínio e dados: reoferta, polos, papéis, tutoria esperada e estados vazios.

Behat

Para validar que o usuário consegue ver e adicionar a atividade no Moodle real.

Resumo final

  • Behat testa o Moodle como um usuário usaria pelo navegador.
  • O teste fica em tests/behat/inline_display.feature.
  • Ele cria dados temporários: curso, usuários, papéis, grupos e atividade.
  • Ele valida estudante, professor e activity chooser.
  • Para JavaScript, usamos Selenium com Chromium.
  • O resultado final foi: 3 scenarios (3 passed).
